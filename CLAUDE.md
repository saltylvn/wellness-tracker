# DEVELOP (wellness tracker)

An iPhone-first web app (installable PWA) for body weight, calorie/macro tracking, lifting workouts, and cardio (run, cycle, swim). The owner is a beginner learning web development with Claude Code, so **explain what each change does and why**, and build in small steps.

## Features
- **Food log:** add food by photo or typed description; AI estimates calories and macros (always editable). Daily totals vs calorie goal.
- **Water:** a slim row on each day of the Nutrition tab: tap +20 oz per bottle (undo available); three steps at 20, 40 and 60 oz, with the third as the daily goal (60 oz). Stored one row per bottle in `water_logs`; logic in `lib/water.ts`.
- **Nutrition tab layout:** header like Fitness ("Nutrition" top-left; Today / Jump to today and the settings gear top-right), streak badge, then a calories card (`CaloriesCard`: one main number inside the `CalorieRing`, "eaten / goal kcal", green at/under goal and red over, with a plain "X kcal left" / "X kcal over" line beside it), then the **macros card** (`MacrosCard`: Protein / Carbs / Fat left to right, each `eaten / goal g` with a thin bar; "Set macro goals" link when none), then the week strip with week arrows (same cell height and layout as the Fitness calendar: a ✅ under each day with food logged, past days dimmed the same way; `WeekStrip`), then a small "Weekday · date" line. Optional protein/carb/fat goals are set in Settings.
- **Consistent sizes across tabs:** Fitness's "Your week" card and Nutrition's macros card are the same size (`TOP_CARD` in `components/cardStyles.ts`, 112px tall); keep new tab layouts lined up the same way.
- **Settings gear:** `SettingsGear` sits top-right on Weight, Fitness and Nutrition and opens the one shared Settings page.
- **Weight tab (`/weight`):** under the header, a weekly weight-loss streak (`WeightStreakBadge`, styled like the other streaks: Mon-Sun weeks in a row whose last weigh-in is at least 1 lb below the previous week's last weigh-in; this week doesn't break it until it's over; a week with no weigh-in ends it; the hint says what to weigh in at to count this week; logic in `lib/weightStreak.ts`, from the ~6 months of weigh-ins the page already loads). Then one card (`WeightProgress`) shows start / current / target with a progress bar, a line chart of weigh-ins with the target line and a dashed projection (`WeightChart`, passed in as `chart`), then lb per week, weeks to go and the goal date. Below it, a compact weigh-in card (no title): a full-width "Weigh in" button across the top ("✓ Weighed in" once saved), two 3-row scroll wheels (pounds 70-500, tenths), and a small status line ("Logged…" with Remove, or "Last…") (`WeighInCard`; one weigh-in per day in `weight_logs`). `WheelPicker` takes optional `rows` (3 or 5) and `showLabel`. Start (optional, else the first weigh-in) and target are set in Settings (`profiles.start_weight_lb`, `profiles.target_weight_lb`). The weekly pace is chosen in Settings ("Weekly pace": 0.5, 1, 1.5 or 2 lb/week, `PACE_CHOICES`; saved in `profiles.weight_pace_lb_week`; blank = 2 lb, `chosenPace` / `WEEKLY_PACE_LB` in `lib/weightPlan.ts`; gaining is capped at 1 lb/week by `clampPace`). Gemini only writes a one-line coaching note told about that pace (`writeWeightCoachNote` in `lib/ai/gemini.ts`, prompt and checks in `lib/ai/weightCoach.ts`), saved on the profile with the numbers it was written for (`weight_coach_key`, which includes the pace); when a weigh-in, start, target or pace changes, `PlanRefresher` asks again. The coach action no longer writes the pace column: it's the user's setting. If the AI is busy or over the daily limit, there's simply no note. All the math is in `lib/weightPlan.ts`; reads go through `lib/weightQueries.ts`.
- **Name and splash:** the app is called DEVELOP (subtitle "wellness tracker"). A logo + name splash shows for about a second on launch, once per browser session (`SplashScreen`, plus a tiny script in `app/layout.tsx` that sets a sessionStorage flag). iOS caches the home-screen name and icon, so after a rename delete the icon and re-add it.
- **Streaks 🔥:** Weight: weekly, see the Weight tab. Nutrition: consecutive days with at least one food entry. Fitness: consecutive days with logged lifting sets or cardio; the Sunday rest day neither breaks nor adds to it; today doesn't break it until the day is over. Shown as a badge with best streak and milestone celebrations; computed in the browser from the user's local date (`lib/streak.ts`).
- **Fitness tab (one page, driven by the week calendar):** green ring around the date on every day with a logged workout or cardio (no check mark; each day shows its 🏋️ / 🏃 / 🧘 icon, or 🏋️🏃 for a lifting and cardio day). Days before today (phone clock) are dimmed, logged or not, so the days ahead stand out (`WorkoutWeekStrip`, a client component). New accounts start with a blank week: all seven days rest, no exercises (`STARTING_PLAN` in `lib/workouts/defaults.ts`, added on the first visit by `loadWorkoutDays` in `lib/workouts/seed.ts`), and a "Build your weekly plan" card shows until a lifting or cardio day is set (`isBlankWeek`). Plans already in the database are untouched (the owner's: Mon Chest & Back, Wed Legs, Fri Delts & Arms, Tue/Thu/Sat cardio, Sun rest; the demo account's is rebuilt by `reset_demo_data`).
  - **Gym check-in barcode:** a card near the top of Fitness (under the streak, above "Your week"), so you can scan in at the gym without opening the gym's app. "Add your gym check-in barcode" / "Change" opens a sheet where you pick a screenshot of a striped barcode (no QR codes: Code 128, Code 39, Code 93, EAN, UPC, ITF, Codabar); the browser reads it (`lib/gymBarcodeDecode.ts`, `@zxing/library`, loaded only when a screenshot is picked; it also tries the picture shrunk, which averages out the faint noise Safari adds to pictures a site reads, and sideways), or "Type the number instead" saves the typed number as Code 128 and only the text and type are saved (`profiles.gym_barcode_text`, `gym_barcode_format`; `20261027000000_gym_barcode.sql`). The server draws a fresh SVG into the page on every load (`lib/gymBarcodeSvg.ts`, `bwip-js/node`), so there's no image to load. Formats and checks in `lib/gymBarcode.ts`; actions in `app/(tabs)/workouts/barcode-actions.ts` (the demo account's sample barcode can't be changed); read in round 1 of `loadFitnessPage` (`loadGymBarcode`); `GymBarcodeCard`.
  - **Your week:** a card under the streak (above the calendar) with two one-line rows of small day toggles, "Lift" and "Cardio", M T W TH F S left to right (no Sunday: it's always a recovery day, enforced on the server too). A day is green when on; the rows are independent: on in both = kind `both` (lifting and cardio on the same day: the page shows the exercises and the cardio logger, titled e.g. "Legs + Cardio"; `hasLift` / `hasCardio`, `20261030000000_lift_and_cardio_days.sql` allows it in the database); off in both = rest. Each tap saves by itself after a short pause (`WeekSetup`, `saveWeekKinds` in `app/(tabs)/workouts/week-actions.ts`, logic in `lib/workouts/weekSetup.ts`). It only changes `workout_days.kind` (and a generic title); exercises stay attached, so switching back restores them. An "Edit plan ›" link in the card's bottom line opens **Edit plan** (`/workouts/plan`, `app/(tabs)/workouts/plan/page.tsx`): the same toggles, then Monday to Sunday with each day's icon, title and exercise count (`loadPlanOverview`); tapping a lifting day opens its editor (`/workouts/plan/[dayId]?from=plan`), and Save / Cancel come back to the week page (`afterDayEditPath`). Cardio and rest days are always titled "Cardio" / "Recovery Day" (`dayTitle`). Tanning stays on Tue/Thu.
  - **Lifting days:** the user's own editable exercise list; supersets shown as a marker between exercises, 3-5 min rest reminders; each lifting day has its own name ("theme", e.g. Legs), set in the "Workout name" box on Edit plan (`parseDayName`, up to 40 characters; blank = "Lifting"; saved with the exercises by `saveDayPlan`); per exercise the user enters their own sets and rep range, and a Log button opens a sheet with scroll wheels for weight (2.5 lb steps) and reps, plus a Weight | Time switch (Weight by default; opens on Time when that exercise's last set was timed) that swaps them for minutes and seconds wheels (5 s steps): a timed set saves only `workout_sets.duration_seconds` (`20261029000000_timed_sets.sql`; `validateTimeInput`, `formatDuration` in `lib/workouts/logging.ts`) and shows as "1:30" / "45 sec"; logged sets show joined by a bold black "+"; last time, today's sets, and heaviest weight show on each card; weight defaults: last used, else 100 lb, dumbbell exercises 25 lb.
  - **Cardio days:** Log run / cycle / swim, each with optional distance (miles for run and cycle, yards for swim) and time; add and delete. Weekly distance goals (Settings): run default 5 mi, cycle default 10 mi, swim no default (yards); blank = no goal. A "This week" card on cardio days shows a progress bar for each, Monday to Sunday.
  - **Tanning (Tue and Thu):** a quiet ☀️ row under the cardio section that shows "Last time: N min" until you log today; tap to pick 5-15 minutes on a scroll wheel (one entry per day, stored in `tanning_logs`). Plain text, no card, and not part of streaks or rings (`lib/tanning.ts`).
- **App icon:** a bold upward line graph of connected dots (white centers, haloed peak dot) in a green gradient (#34c759 to #1a9e3a), on a background fading from white to iOS light grey (#f2f2f7), matching the always-light app. The design is drawn in code (`lib/appIcon.tsx`), but the phone and browsers use plain, solid (no transparency) PNG files in `public/`: `apple-touch-icon.png` (180, home screen), `icon-192.png` and `icon-512.png` (manifest and tabs), linked in `app/layout.tsx` metadata and `app/manifest.ts`. After changing the design, run `npm run dev` then `npm run icons` (`scripts/make-icons.sh`, using the dev-only `/icon-source/[size]` route; it strips photo metadata with `scripts/strip-png.mjs` and writes an `apple-touch-icon-precomposed.png` copy), then bump `ICON_VERSION` in `lib/iconVersion.ts` (added to the icon links as `?v=`, so phones fetch the new file instead of a saved old one) and commit the PNGs. iPhones allow only one home-screen icon (no light/dark switching) and cache it: delete the home-screen icon and re-add it after a change.
- **Tabs:** three bottom tabs, left to right: Weight (`/weight`), Fitness (`/workouts`), Nutrition (`/food`). The app opens on Fitness: `/`, the manifest `start_url`, sign-in (Google and demo) and `/login` when signed in all go to `/workouts`.

## Stack
Next.js (App Router) + TypeScript, Tailwind CSS, Supabase (Postgres, auth, storage), Google Gemini free tier for AI food estimates (server-side only, via `lib/ai/gemini.ts`, the one swappable provider file), deployed on Vercel.

## Conventions
- Always light: white background with the green accent, even when the phone is in dark mode (no `prefers-color-scheme: dark` styles; `color-scheme: light` in `app/globals.css`; white `themeColor` and manifest colors). The app icon is white too.
- Text on the bright green accent is always black (`--on-accent` in `app/globals.css`); use `text-on-accent` on `bg-accent`, never `text-white`.
- Mobile-first: design for ~390px width, safe-area insets, 44px+ tap targets, 16px+ input font size (prevents iOS zoom).
- The Anthropic API key and Supabase service key live only in `.env.local` (git-ignored). Never expose them to browser code.
- Call the AI only from the server (`app/api/estimate-food/route.ts`, `app/(tabs)/weight/actions.ts`); validate the JSON reply before using it (`lib/ai/nutrition.ts`, `lib/ai/weightCoach.ts`). Both share one 40-a-day AI limit per user (`lib/ai/dailyLimit.ts`). `GEMINI_API_KEY` lives only in `.env.local` and Vercel (Sensitive).
- Row-level security on every Supabase table; every table is scoped to the signed-in user.
- Content Security Policy: `proxy.ts` sends a per-request nonce CSP built by `lib/csp.ts` (tested); the root layout reads `x-nonce` for its one inline script. Any new inline `<script>` needs `nonce={nonce}`; a new external host (images, fetch, sign-in redirect) must be added to `buildCsp`. Other headers (Permissions-Policy, COOP, nosniff, framing, referrer) are in `next.config.ts`.
- AI daily limit: `takeAiRequest` calls the `take_ai_request` Postgres function (one round trip, per-user lock; `20261026000000_ai_limit_function.sql`) and falls back to count-then-insert if that SQL isn't installed.
- Recruiter demo: "Try the demo" on the login page (`DemoSignInButton`, `signInAsDemo` in `app/login/actions.ts`) signs in to the shared `demo@example.com` account with `DEMO_EMAIL`/`DEMO_PASSWORD` (server-only env; button hidden when unset), then calls `reset_demo_data(today)` (`supabase/migrations/20261025000000_recruiter_demo.sql`), which rebuilds sample data relative to the visitor's date at most hourly and only for the demo account; it never clears `ai_requests`. `DemoBanner` shows on every tab in the demo. If you add a table, add it to the demo reset (and seed it if it should show data).
- At most 25 accounts (personal/portfolio app, not built to scale): a `before insert` trigger on `auth.users` refuses the 26th (`supabase/migrations/20261024000000_user_cap.sql`); `/auth/callback` maps Supabase's "Database error saving new user" to `/login?error=full` (`lib/authErrors.ts`, `MAX_USERS`, keep in step with the SQL).
- Dates are stored as the user's local calendar date, not UTC timestamps, so daily totals and streaks don't break at midnight.
- Keep pure logic (streaks, goal status) in `lib/` with unit tests.
- Server actions share `lib/actionResult.ts` (the `ActionResult` type, `currentUserId`, `failedSave`); don't repeat the sign-in and error boilerplate. Those lib files use relative imports so vitest can load them.
- The Fitness page reads its data through `loadFitnessPage` in `lib/workouts/queries.ts`, in two rounds of parallel queries (round 1: plan, logged days, the weekday's exercises by weekday, tanning, gym barcode; round 2: the lift and/or cardio data, in parallel). A test in `queries.test.ts` times it against a 50 ms stand-in database and fails if a lifting, cardio, or lifting-and-cardio day takes more than 2 trips. Add new reads there, not inline in `page.tsx`.
- Performance: tab links and "Jump to today" include `?date=` (from the phone's clock), so a tab tap loads the page once instead of bouncing through `GoToToday`; each tab has a `loading.tsx` (`PageSkeleton`) so taps respond instantly; "Continue with Google" starts on the server (`app/login/actions.ts`), so no Supabase code is sent to the browser; `WheelPicker` rows are memoized. Use `currentUserId` for sign-in checks.
- Small, focused git commits with clear messages.
- `main` is protected (GitHub ruleset "Protect main"): every change, including CLAUDE.md updates, goes through a pull request, Vercel's build check must pass before merging, and force-pushes and deleting `main` are blocked. No reviewer approval is required.

- This is Next.js 16 (newer than most tutorials). Check the bundled docs in `node_modules/next/dist/docs/` before using a Next.js API (see `AGENTS.md`).
- Today's date in the browser comes from the shared `useToday()` hook (`components/useToday.ts`; null on the server).
- Browser-only code goes in components marked `"use client"` (see `components/`); pages in `app/` are server components by default.

## Commands
- `npm run dev`: start the local dev server
- `npm run build`: production build
- `npm test`: run unit tests (vitest; pure logic in `lib/`)
- On GitHub, every PR runs CI (`.github/workflows/ci.yml`: lint, `tsc --noEmit`, tests; about 30 s); it and Vercel's build must pass before merging. Dependabot opens grouped update PRs weekly (`.github/dependabot.yml`); actions are pinned to commit SHAs (required by the repo settings).
