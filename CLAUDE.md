# DEVELOP (wellness tracker)

An iPhone-first web app (installable PWA) for body weight, calorie/macro tracking, lifting workouts, and cardio (run, cycle, swim). The owner is a beginner learning web development with Claude Code, so **explain what each change does and why**, and build in small steps.

## Features
- **Food log:** the "+ Log food" button (the "Log food" page and its "Log food" save button; called "Add food" before) logs food by photo or typed description; AI estimates calories and macros (always editable). Daily totals vs calorie goal.
- **Water:** a slim row on each day of the Nutrition tab: tap +20 oz per bottle (undo available); three steps at 20, 40 and 60 oz, with the third as the daily goal (60 oz). Stored one row per bottle in `water_logs`; logic in `lib/water.ts`.
- **Nutrition tab layout:** header like Fitness ("Nutrition" top-left; Today / Jump to today and the settings gear top-right), streak badge, then the week strip with week arrows right under it (no separate date line: the strip shows the day), then a calories card (`CaloriesCard`: one main number inside the `CalorieRing`, "eaten / goal kcal", orange at/under goal and red over, with a plain "X kcal left" / "X kcal over" line beside it), then the **macros card** (`MacrosCard`: Protein / Carbs / Fat left to right, each `eaten / goal g` with a thin bar; "Set macro goals" link when none), (the week strip has the same cell height and layout as the Fitness calendar: an orange check (drawn in the app, not the green ✅ emoji) under each day with food logged, past days dimmed the same way; `WeekStrip`). Optional protein/carb/fat goals are set in Settings.
- **Consistent sizes across tabs:** every tab starts the same way: a `<header className="space-y-4">` with the title row (title left; Today and the settings gear right), then the streak card, then the week calendar with arrows right under it (no date line on any tab), then the tab's own cards (Weight: weigh-in, progress; Fitness: "Your week", the gym barcode; Nutrition: calories, macros). The streak card has one fixed size on all three tabs (`STREAK_CARD` in `components/cardStyles.ts`, 76px tall, the hint cut short with "…" rather than wrapping; `STREAK_PLACEHOLDER` holds its place until the phone's date is known), so it sits in exactly the same spot on Weight, Fitness and Nutrition. Fitness's "Your week" card and Nutrition's macros card are the same size too (`TOP_CARD`, 112px tall); keep new tab layouts lined up the same way.
- **Settings gear:** `SettingsGear` sits top-right on Weight, Fitness and Nutrition and opens the one shared Settings page.
- **Weight tab (`/weight`):** the title "Weight" (no date line under it: the calendar shows the day), then a weekly weight-loss streak (`WeightStreakBadge`, styled like the other streaks: Mon-Sun weeks in a row whose last weigh-in is at least 1 lb below the previous week's last weigh-in; this week doesn't break it until it's over; a week with no weigh-in ends it; the hint says what to weigh in at to count this week; logic in `lib/weightStreak.ts`, from the weigh-ins the page already loads). Then a small week calendar like Fitness's (`WeightWeekStrip`, reusing `WorkoutWeekStrip` with no day icons: Monday to Sunday with week arrows, an orange ring on each day with a weigh-in, from `weekLogged` in `loadWeightData`; tap a day to weigh in for it). Then the weigh-in card (`WeighInCard`): just an orange "Weigh in" button ("✓ Weighed in" once that day has one) and a small status line ("Logged…" with Remove, or "Last…"); the button slides up a log window (`BottomSheet`) with the pounds (70-500) and tenths wheels and a "Save 201.8 lb" button, so no numbers show until you tap it (one weigh-in per day in `weight_logs`). Below it, one card (`WeightProgress`) shows start / current / target with a progress bar, under the bar "12.1 of 30.0 lb lost" and the percent in bold black, then a line chart of weigh-ins (`WeightChart`, about 140 tall in its drawing units: a soft orange fill under the line, a small dot on each weigh-in (up to 40), the latest weight labeled with a halo, dashed grid, first / middle / last dates; it runs from your first weigh-in to today and is scaled to your weigh-ins (`chartRange` in `lib/weightPlan.ts`), with the target line only when it fits; no projection; passed in as `chart`; `loadWeightData` reads every weigh-in, not just recent ones), then lb per week, weeks to go and the goal date, and one line with the last-4-weeks trend and an "Edit goal" link to Settings. `WheelPicker` takes optional `rows` (3 or 5) and `showLabel`. Start weight and starting date (both optional, else the first weigh-in) and target are set in Settings (`profiles.start_weight_lb`, `profiles.start_date`, `profiles.target_weight_lb`; `20261107000000_start_date.sql`; the date is read with `select("*")` so pages load before the SQL step, and `saveGoals` skips it when blank and the column is missing); the progress and chart use only weigh-ins from the starting date on, beginning at the starting weight on that date (`weighInsSinceStart`). "Edit goal" opens `/settings#weight-goal`. The weekly pace is chosen in Settings ("Weekly pace": 0.5, 1, 1.5 or 2 lb/week, `PACE_CHOICES`; saved in `profiles.weight_pace_lb_week`; blank = 2 lb, `chosenPace` / `WEEKLY_PACE_LB` in `lib/weightPlan.ts`; gaining is capped at 1 lb/week by `clampPace`). There is no AI coach any more (removed at the owner's request; the old `weight_coach_*` profile columns are simply unused). All the math is in `lib/weightPlan.ts`; reads go through `lib/weightQueries.ts`.
- **Name and splash:** the app is called DEVELOP (subtitle "wellness tracker"). A logo + name splash shows for about a second on launch, once per browser session (`SplashScreen`, plus a tiny script in `app/layout.tsx` that sets a sessionStorage flag). iOS caches the home-screen name and icon, so after a rename delete the icon and re-add it.
- **Streaks 🔥:** Weight: weekly, see the Weight tab. Nutrition: consecutive days with at least one food entry. Fitness: consecutive days with logged lifting sets or cardio (a completed rest day walk, ride or yoga counts as cardio); planned rest days neither break nor add to it on their own; today doesn't break it until the day is over. Shown as a badge with best streak and milestone celebrations; computed in the browser from the user's local date (`lib/streak.ts`).
- **Fitness tab (one page, driven by the week calendar):** orange ring around the date on every day with a logged workout or cardio (no check mark; each day shows its 🏋️ / 🏃 / 🧘 icon, or 🏋️🏃 for a lifting and cardio day). The calendar shows Monday to Sunday. Days before today (phone clock) are dimmed, logged or not, so the days ahead stand out (`WorkoutWeekStrip`, a client component). New accounts start with a blank week: all seven days rest, no exercises (`STARTING_PLAN` in `lib/workouts/defaults.ts`, added on the first visit by `loadWorkoutDays` in `lib/workouts/seed.ts`), and a "Build your weekly plan" card shows until a lifting or cardio day is set (`isBlankWeek`). Plans already in the database are untouched (the owner's: Mon Chest & Back, Wed Legs, Fri Delts & Arms, Tue/Thu/Sat cardio, Sun rest; the demo account's is rebuilt by `reset_demo_data`).
  - **Gym check-in barcode:** a card on Fitness below the week calendar (after the streak, "Your week" and the calendar), so you can scan in at the gym without opening the gym's app. "Add your gym check-in barcode" / "Change" opens a sheet where you pick a screenshot of a striped barcode (no QR codes: Code 128, Code 39, Code 93, EAN, UPC, ITF, Codabar); the browser reads it (`lib/gymBarcodeDecode.ts`, `@zxing/library`, loaded only when a screenshot is picked; it also tries the picture shrunk, which averages out the faint noise Safari adds to pictures a site reads, and sideways), or "Type the number instead" saves the typed number as Code 128 and only the text and type are saved (`profiles.gym_barcode_text`, `gym_barcode_format`; `20261027000000_gym_barcode.sql`). The server draws a fresh SVG into the page on every load (`lib/gymBarcodeSvg.ts`, `bwip-js/node`), so there's no image to load. Formats and checks in `lib/gymBarcode.ts`; actions in `app/(tabs)/workouts/barcode-actions.ts` (the demo account's sample barcode can't be changed); read in round 1 of `loadFitnessPage` (`loadGymBarcode`); `GymBarcodeCard`.
  - **Your week:** a card below the calendar (the calendar sits right under the streak, as on the other tabs) with two one-line rows of small day toggles, "Lift" and "Cardio", M T W TH F SA SU left to right (every day can be planned, Sunday included; same size as Nutrition's macros card, `TOP_CARD`). A day is orange when on; the rows are independent: on in both = kind `both` (lifting and cardio on the same day: the page shows the exercises and the cardio logger, titled e.g. "Legs + Cardio"; `hasLift` / `hasCardio`, `20261030000000_lift_and_cardio_days.sql` allows it in the database); off in both = rest. Each tap saves by itself after a short pause (`WeekSetup`, `saveWeekKinds` in `app/(tabs)/workouts/week-actions.ts`, logic in `lib/workouts/weekSetup.ts`). It only changes `workout_days.kind` (and a generic title); exercises stay attached, so switching back restores them. An "Edit plan ›" link in the card's bottom line opens **Edit plan** (`/workouts/plan`, `app/(tabs)/workouts/plan/page.tsx`): the same toggles, then Monday to Sunday with each day's icon, title, exercise count and cardio plan (`loadPlanOverview`); tapping a lifting or cardio day opens its editor (`/workouts/plan/[dayId]?from=plan`), and Save / Cancel come back to the week page (`afterDayEditPath`). Settings, Edit plan and each day's editor have a "‹ Back" button top-left (`BackButton`: the browser's back, or a fallback page when there's no history). Cardio and rest days are always titled "Cardio" / "Recovery Day" (`dayTitle`).
  - **Lifting days:** the user's own editable exercise list; supersets shown as a marker between exercises, 3-5 min rest reminders; each lifting day has its own name ("theme", e.g. Legs), set in the "Workout name" box on Edit plan (`parseDayName`, up to 40 characters; blank = "Lifting"; saved with the exercises by `saveDayPlan`); per exercise the user enters their own sets and rep range, and a Log button opens a sheet with scroll wheels for weight (2.5 lb steps) and reps, plus a Weight | Time switch (Weight by default; opens on Time when that exercise's last set was timed) that swaps them for minutes and seconds wheels (5 s steps): a timed set saves only `workout_sets.duration_seconds` (`20261029000000_timed_sets.sql`; `validateTimeInput`, `formatDuration` in `lib/workouts/logging.ts`) and shows as "1:30" / "45 sec"; logged sets show joined by a bold black "+"; each card is compact (`LogExercise`, about 74px: the name, then the target and 🏆 heaviest weight on one small line, then today's sets or last time, with the Log button beside them, not below; cards and the rest / superset notes between them are spaced tightly), so more exercises fit on screen; weight defaults: last used, else 100 lb, dumbbell exercises 25 lb.
  - **Priority lifts:** up to two exercises you're focusing on, picked in Settings from your plan's exercise names (`PriorityLiftsForm`, `savePriorityLifts`; saved by name in `profiles.priority_lift_1` / `priority_lift_2`, `20261102000000_priority_lifts.sql`; logic and tests in `lib/priorityLifts.ts`). On every lifting day, two slim outlined pills sit one above the other (full width, so longer names fit) above the exercises, one line each: an orange ★, the name (cut short with "…" if long) and "PR 225" = heaviest weight ever logged under that name, or "PR –" (`PriorityLifts`, about 34px tall each). Names are read in round 1 of `loadFitnessPage` (`select("*")`, so it works before the SQL step) and the bests in round 2 (`loadPriorityBests`). The demo account shows Squats and Deadlift.
  - **Cardio days:** planned ahead, then completed. On Edit plan a cardio day (or a lifting and cardio day) gets one of run / cycle / swim plus an optional target in miles, km, meters, yards (swims) or time (minutes) (`CardioPlanFields` in the day editor, saved by `saveDayPlan` to `workout_days.cardio_plan_kind` / `cardio_plan_distance` / `cardio_plan_unit`; `20261031000000_cardio_day_plan.sql`, `20261101000000_cardio_plan_unit.sql`; logic and tests in `lib/cardioPlan.ts`; empty unit = miles, or yards for a swim). On the day, under a "Tuesday's cardio" heading with an "Edit plan" link on the right (same row as the exercises' heading), `PlannedCardio` shows it ("Planned" / "🏃 Run · 5 km") with a **Completed** box: ticking it logs that cardio for the day (`setPlannedCardioDone` reads the plan from the database; `planToLog` converts a distance to miles, or yards for swims, so it counts toward the weekly goals, and a time target becomes the log's minutes), unticking removes it; ticked whenever a log of the planned kind exists that day (`completingLog`). No plan: a "Plan this day's cardio" link. There are no free-form Log run / cycle / swim buttons any more. Plan columns are read with `select("*")` on their own (`loadCardioPlan`, round 1 of `loadFitnessPage`), so pages still load before the SQL steps. Weekly distance goals (Settings): run default 5 mi, cycle default 10 mi, swim no default (yards), walk (miles, `profiles.weekly_walk_miles`, no default; walk is a fourth `CARDIO_KINDS` entry, so cardio days can plan walks too); blank = no goal. A compact "This week" card on cardio and rest days (`WeeklyCardioGoals`, about 100px) shows one line for each: name, thin progress bar, "done / goal" (🎯 once reached), Monday to Sunday.
  - **Rest days:** planned like cardio days. On Edit plan a rest day opens its editor too (titled "Edit Recovery Day"), with a Walk / Bike ride / Yoga / None picker and an optional target, miles for a walk or ride, minutes for yoga (`RestPlanFields`, saved by `saveDayPlan` to `workout_days.rest_plan_activity` / `rest_plan_target`; logic and tests in `lib/restPlan.ts`). On the day, under a "Sunday's recovery" heading with "Edit plan" on the right, `PlannedRest` shows it ("Planned" / "🚶 Walk · 2 mi") with a **Completed** box (`setRestPlanDone` in `cardio-actions.ts`): ticking it logs a `cardio_logs` row, a walk as kind `walk` in miles (counts toward the weekly walking goal), a bike ride as `cycle` (toward cycling), yoga as `yoga` in minutes; so a completed rest day also gets the orange ring and adds to the streak. No plan: a "Plan a walk, bike ride or yoga" link. The "This week" goals card shows on rest days too (`loadCardioDay` runs for cardio and rest days). One SQL step: `20261104000000_rest_day_plan.sql` (the two plan columns, `walk` and `yoga` allowed in `cardio_logs.kind`, and `profiles.weekly_walk_miles`).
  - **Sunshine (every day, was Tanning):** a quiet ☀️ row ("☀️ Sunshine 10 / 20 min", orange with ✓ once the daily target is reached; without a target, today's minutes or "Last time: N min") at the very bottom of the page, every day; tap to pick 5-60 minutes on a scroll wheel (one entry per day). ## Stack
Next.js (App Router) + TypeScript, Tailwind CSS, Supabase (Postgres, auth, storage), Google Gemini free tier for AI food estimates (server-side only, via `lib/ai/gemini.ts`, the one swappable provider file), deployed on Vercel.

## Conventions
- Always light, minimal orange and white (styled after the user's reference screenshots): a light grey page (`--background` #f4f4f5) with white cards (`bg-card`, which gets a soft shadow from `--card-shadow` in `app/globals.css`, and rounder `rounded-2xl` corners, 24px via `--radius-2xl`), the orange accent (`--accent` #f26b2a) for rings, bars and highlights, and pill-shaped main buttons (`rounded-full bg-accent`). It stays light even when the phone is in dark mode (no `prefers-color-scheme: dark` styles; `color-scheme: light`); `themeColor` and the manifest colors match the light grey page.
- Text on the orange accent is white (`--on-accent`); always use `text-on-accent` on `bg-accent`, so the pair can change in one place.
- Mobile-first: design for ~390px width, safe-area insets, 44px+ tap targets, 16px+ input font size (prevents iOS zoom).
- The Anthropic API key and Supabase service key live only in `.env.local` (git-ignored). Never expose them to browser code.
- Call the AI only from the server (`app/api/estimate-food/route.ts`, the food estimates); validate the JSON reply before using it (`lib/ai/nutrition.ts`). It has a 40-a-day AI limit per user (`lib/ai/dailyLimit.ts`). `GEMINI_API_KEY` lives only in `.env.local` and Vercel (Sensitive).
- Row-level security on every Supabase table; every table is scoped to the signed-in user.
- Content Security Policy: `proxy.ts` sends a per-request nonce CSP built by `lib/csp.ts` (tested); the root layout reads `x-nonce` for its one inline script. Any new inline `<script>` needs `nonce={nonce}`; a new external host (images, fetch, sign-in redirect) must be added to `buildCsp`. Other headers (Permissions-Policy, COOP, nosniff, framing, referrer) are in `next.config.ts`.
- AI daily limit: `takeAiRequest` calls the `take_ai_request` Postgres function (one round trip, per-user lock; `20261026000000_ai_limit_function.sql`) and falls back to count-then-insert if that SQL isn't installed.
- Recruiter demo: "Try the demo" on the login page (`DemoSignInButton`, `signInAsDemo` in `app/login/actions.ts`) signs in to the shared `demo@example.com` account with `DEMO_EMAIL`/`DEMO_PASSWORD` (server-only env; button hidden when unset), then calls `reset_demo_data(today)` (`supabase/migrations/20261025000000_recruiter_demo.sql`), which rebuilds sample data relative to the visitor's date at most hourly and only for the demo account; it never clears `ai_requests`. `DemoBanner` shows on every tab in the demo. If you add a table, add it to the demo reset (and seed it if it should show data).
- At most 25 accounts (personal/portfolio app, not built to scale): a `before insert` trigger on `auth.users` refuses the 26th (`supabase/migrations/20261024000000_user_cap.sql`); `/auth/callback` maps Supabase's "Database error saving new user" to `/login?error=invite` (`lib/authErrors.ts`, `MAX_USERS`, keep in step with the SQL).
- Dates are stored as the user's local calendar date, not UTC timestamps, so daily totals and streaks don't break at midnight.
- Keep pure logic (streaks, goal status) in `lib/` with unit tests.
- Server actions share `lib/actionResult.ts` (the `ActionResult` type, `currentUserId`, `failedSave`); don't repeat the sign-in and error boilerplate. Those lib files use relative imports so vitest can load them.
- The Fitness page reads its data through `loadFitnessPage` in `lib/workouts/queries.ts`, in two rounds of parallel queries (round 1: plan, logged days, the weekday's exercises by weekday, sunshine, gym barcode; round 2: the lift and/or cardio data, in parallel). A test in `queries.test.ts` times it against a 50 ms stand-in database and fails if a lifting, cardio, or lifting-and-cardio day takes more than 2 trips. Add new reads there, not inline in `page.tsx`.
- Performance: tab links and "Jump to today" include `?date=` (from the phone's clock), so a tab tap loads the page once instead of bouncing through `GoToToday`; each tab has a `loading.tsx` (`PageSkeleton`) so taps respond instantly; "Continue with Google" starts on the server (`app/login/actions.ts`), so no Supabase code is sent to the browser; `WheelPicker` rows are memoized. Use `currentUserId` for sign-in checks.
- Small, focused git commits with clear messages.
- `main` is protected (GitHub ruleset "Protect main"): every change, including CLAUDE.md updates, goes through a pull request, Vercel's build check must pass before merging, and force-pushes and deleting `main` are blocked. No reviewer approval is required.

- This is Next.js 16 (newer than most tutorials). Check the bundled docs in `node_modules/next/dist/docs/` before using a Next.js API (see `AGENTS.md`).
- Today's date in the browser comes from the shared `useToday()` hook (`components/useToday.ts`; null on the server).
- Browser-only code goes in components marked `"use client"` (see `components/`); pages in `app/` are server components by default.

## Commands
- `npm run dev`: start the local dev server
- `npm run build`: production build
- `npm test`: run unit tests (vitest; pure logic in `lib/`)
- On GitHub, every PR runs CI (`.github/workflows/ci.yml`: lint, `tsc --noEmit`, tests; about 30 s); it and Vercel's build must pass before merging. Dependabot opens grouped update PRs weekly (`.github/dependabot.yml`); actions are pinned to commit SHAs (required by the repo settings).
